## 3. Verified API + Kotlin snippets

Signatures taken from `javap` on the real jar; every snippet below was compiled with `kotlinc` and
**executed** on JDK 11. Package root is `com.nlf.calendar` (note: *not* `com.6tail`, despite the
groupId).

### (a) Gregorian → lunar month/day name (incl. leap month)

```kotlin
import com.nlf.calendar.Solar

val lunar = Solar.fromYmd(2024, 2, 10).lunar       // Solar.getLunar()
val text  = "${lunar.yearInChinese}年${lunar.monthInChinese}月${lunar.dayInChinese}"
// -> "二〇二四年正月初一"

val isLeapMonth = lunar.month < 0                  // Lunar.getMonth() is NEGATIVE for 闰月
```

Verified output (actual program output):

| Gregorian | `lunar.month` | Result |
|---|---|---|
| 2024-02-10 | 1 | 二〇二四年**正月初一** |
| 2024-02-09 | 12 | 二〇二三年**腊月三十** |
| 2024-02-03 | 12 | 二〇二三年**腊月廿四** |
| 2025-01-22 | 12 | 二〇二四年**腊月廿三** |
| 2023-03-22 | **-2** | 二〇二三年**闰二月初一** |

> ### ⚠️ Trap: `getMonthInChinese()` already contains "闰"
> For a leap month it returns **`"闰二"`**, not `"二"`. Writing
> `"${lunar.yearInChinese}年闰${lunar.monthInChinese}月${lunar.dayInChinese}"` produces the
> nonsense **`闰闰二月初一`** — I reproduced this exact bug. Use `lunar.monthInChinese` alone
> (as above), or just call `lunar.toString()`, which yields the correct
> `二〇二三年闰二月初一`.

**Reverse direction (lunar → Gregorian)**, leap months via negative month:

```kotlin
import com.nlf.calendar.Lunar

Lunar.fromYmd(2024, 1, 1).solar.toYmd()   // "2024-02-10"  正月初一
Lunar.fromYmd(2023, -2, 1).solar.toYmd()  // "2023-03-22"  闰二月初一
```

`Lunar.fromDate(java.util.Date)` also exists (timezone-sensitive — prefer the `fromYmd` factories).

### (b) Solar term (二十四节气) for a date

```kotlin
import com.nlf.calendar.Solar

val lunar = Solar.fromYmd(2024, 2, 4).lunar

val termToday: String = lunar.jieQi        // "立春" — or "" if this date is NOT a solar-term day
val current  = lunar.currentJieQi          // JieQi?  — null on non-term days
val next     = lunar.nextJieQi             // JieQi   — never null for valid dates
next.name                                   // "雨水"
next.solar.toYmd()                          // "2024-02-19"
```

Verified output:

| Date | `getJieQi()` | `currentJieQi` | `nextJieQi` |
|---|---|---|---|
| 2024-02-04 | **立春** | 立春 | 立春 @2024-02-04 |
| 2024-02-05 | **`""`** (none) | `null` | 雨水 @2024-02-19 |
| 2024-12-21 | **冬至** | 冬至 | 冬至 @2024-12-21 |
| 2025-04-04 | **清明** | 清明 | 清明 @2025-04-04 |
| 2026-03-20 | **春分** | 春分 | 春分 @2026-03-20 |

`lunar.jieQiTable` gives the whole year as `Map<String, Solar>` (31 entries, including ASCII alias
keys such as `DA_XUE` alongside the Chinese ones). `JieQi.isJie()` / `isQi()` distinguish 节 from 气.

This is a genuinely good fit for requirement 2: `getJieQi()` answers "*is* this date a solar term,
and which" in one call.

### (c) Holiday / 休 vs 班(调休) vs normal

```kotlin
import com.nlf.calendar.util.HolidayUtil

val h = HolidayUtil.getHoliday(2024, 2, 4)   // Holiday?  -> null means "normal day"
val kind = when {
    h == null  -> "NORMAL"          // not a holiday, not a makeup workday
    h.isWork   -> "班 (调休)"        // adjusted WORKDAY: isWork() == true
    else       -> "休"               // public holiday
}
h?.name    // "春节"
h?.day     // "2024-02-04"   (already YYYY-MM-DD)
h?.target  // "2024-02-10"   (the festival this day is attached to)
```

Verified output (real program):

| Date | Result | name | target |
|---|---|---|---|
| 2024-02-10 | **休** | 春节 | 2024-02-10 |
| 2024-02-04 | **班** | 春节 | 2024-02-10 |
| 2024-02-18 | **班** | 春节 | 2024-02-10 |
| 2024-02-06 | NORMAL (`null`) | – | – |
| 2024-04-07 | **班** | 清明节 | 2024-04-04 |
| 2024-05-11 | **班** | 劳动节 | 2024-05-01 |
| 2024-10-12 | **班** | 国庆节 | 2024-10-01 |
| 2025-01-26 | **班** | 春节 | 2025-01-29 |
| 2025-10-11 | **班** | 国庆中秋 | 2025-10-01 |
| 2026-02-14 | **班** | 春节 | 2026-02-17 |
| 2026-10-10 | **班** | 国庆节 | 2026-10-01 |

Other verified entry points:

```kotlin
HolidayUtil.getHoliday("2024-02-10")            // String overload, "-" tolerated
HolidayUtil.getHolidays(2024)                   // List<Holiday> for a whole year
HolidayUtil.getHolidays(2024, 2)                // List<Holiday> for a month
HolidayUtil.getHolidaysByTarget("2024-02-10")   // all days belonging to one festival
// -> 10 days: 02-04(班) 02-10..02-17(休) 02-18(班)
```

Default names: `HolidayUtil.NAMES = [元旦节, 春节, 清明节, 劳动节, 端午节, 中秋节, 国庆节, 国庆中秋, 抗战胜利日]`.

### (d) 干支 / 生肖

```kotlin
val l = Solar.fromYmd(2024, 2, 10).lunar
l.yearInGanZhi    // 甲辰
l.yearShengXiao   // 龙
l.monthInGanZhi   // 丙寅
l.dayInGanZhi     // 甲辰
l.dayNaYin        // 覆灯火
```

> ⚠️ **Three different year boundaries** — this is a correctness trap, choose deliberately:
> `getYearInGanZhi()` switches at **正月初一**, `getYearInGanZhiByLiChun()` at **立春**,
> `getYearInGanZhiExact()` at the **exact 立春 instant**.
> Verified divergence: for **2025-01-29**, `yearInGanZhi` = **乙巳 / 蛇** but
> `yearInGanZhiByLiChun` = **甲辰 / 龙**. For a "Chinese New Year" app the default
> (`getYearInGanZhi` / `getYearShengXiao`) is the conventional choice.

## 4. Holiday data coverage & out-of-range behaviour

Measured by iterating `HolidayUtil.getHolidays(year)` for 1999–2032:

- **Earliest record: 2001-12-29**
- **Latest record: 2026-10-10**
- **860 records total**, covering years **2001 … 2026** (contiguous)
- Years 1999, 2000 and 2027–2032 return **0 records**

**Out-of-range behaviour is safe, not exceptional:**

- `getHoliday(y, m, d)` → returns **`null`** (verified for 2026-10-11, 2027-01-01, 2027-10-01,
  2030-05-01, 2001-12-28, 2000-01-01, 1999-10-01).
- `getHolidays(year)` → returns an **empty list** (verified for 2027–2032).

So a null/unrecorded day simply means "no holiday record" → treat as a normal day. Nothing throws.

Since **today is 2026-10-01**, 2026 is effectively fully covered (the last 调休 of the year,
2026-10-10, is present; the next holiday after that is 2027 New Year). The real gap is **2027+**,
which *no* library can have yet because 国务院 has not published the 2027 schedule.

### Patching future years: `HolidayUtil.fix()` — verified working

Record format is **18 chars**: `YYYYMMDD` + `nameIndex(1)` + `workFlag(1)` + `targetYYYYMMDD(8)`,
where `nameIndex` indexes `HolidayUtil.NAMES` and `workFlag == '0'` means `isWork()==true` (班/调休),
anything else means 休. **Verified by execution** (2027 was empty before, populated after):

```kotlin
// 2027-01-01: day + nameIdx 0(元旦节) + '1'(休) + target 20270101
HolidayUtil.fix("202701010120270101")
// 2027-01-02: day + nameIdx 0(元旦节) + '0'(班/调休) + target 20270101
HolidayUtil.fix("202701020020270101")

HolidayUtil.getHoliday(2027, 1, 1)   // -> 2027-01-01 元旦节 2027-01-01   (isWork=false)
HolidayUtil.getHoliday(2027, 1, 2)   // -> 2027-01-02 元旦节调休 2027-01-01 (isWork=true)
HolidayUtil.getHolidays(2027).size   // -> 2
```

`fix()` mutates **static** state → call it **once at startup**, never per-render. (Note: I initially
passed a wrong name-index digit and got 春节 instead of 元旦节 — the library behaved exactly per
spec, so the digit positions above are confirmed, not inferred.)

## 5. Alternatives compared

| Library | Lunar + 闰月 | 节气 | Holiday + 调休 | Coverage | License | Verdict |
|---|---|---|---|---|---|---|
| **`cn.6tail:lunar` 1.7.7** | ✅ | ✅ `getJieQi()` | ✅ | 2001-12-29 → 2026-10-10 | **MIT** | **Recommended** |
| `cn.6tail:tyme4j` 1.5.2 | ✅ `isLeap()` | ⚠️ enclosing period only | ✅ `LegalHoliday` | same dataset (860 recs, same end date) | MIT | Viable, newer, rougher |
| `com.ibm.icu:icu4j` 78.3 | ✅ `IS_LEAP_MONTH` | ❌ **none** | ❌ **none** | – | Unicode | **Fails reqs 2 & 3** |
| `xyz.xiamang:holiday` 0.0.5-2025 | ❌ | ❌ | holidays only | per-year artifacts | Apache-2.0 | Too narrow/immature |
| `de.focus-shift:jollyday` 2.21.0 | ❌ | ❌ | ❌ **no China file at all** | – | Apache-2.0 | Not applicable |
| JitPack `com.github.6tail:lunar-java:1.7.7` | ✅ | ✅ | ✅ | same | MIT | Works, but needs extra repo |

**tyme4j** is by the same author and self-described as "Lunar 的升级版" (upgraded Lunar); GitHub shows
231 stars vs lunar-java's 970. Verified via `javap` + execution: `SolarDay.fromYmd(...).term`,
`SolarDay.getLegalHoliday()`, `LunarDay.getLunarMonth().isLeap()`, and `getMonthValue()` returning
**`-2`** for 闰二月 with `getName()` returning **`"闰二月"`**. Its `LegalHoliday.DATA` parses to
exactly **860 records spanning 2001-12-29 → 2026-10-10** — the same dataset.

Why tyme4j is *not* my recommendation:

1. **`SolarDay.getTerm()` returns the enclosing term period, not "is today a term day."**
   For **2024-02-05** it returned `立春` ("立春第2天"), whereas lunar-java's `getJieQi()` correctly
   returned `""`. You'd have to inspect the day index yourself — an easy off-by-one bug for
   requirement 2.
2. `LunarDay.getYearSixtyCycle()` is **deprecated** (kotlinc emitted a deprecation warning).
3. Smaller community / less battle-tested, docs Chinese-only as well.

**ICU4J** deserves explicit rejection: I read the `ChineseCalendar` javadoc — its entire public
surface is `Calendar` machinery (`add`, `roll`, `handleComputeFields`, `IS_LEAP_MONTH`,
`getGregorianYear`, …). There is **no solar-term API and no PRC statutory holiday/调休 data**, so it
cannot satisfy requirements 2 and 3; it is also a very large jar. Keep `kotlinx-datetime` for
ordinary date math (already a dependency) rather than pulling ICU4J.

## 6. Caveats

- **Docs are Chinese-only.** README and all Javadoc comments are Chinese; the API reference is
  `https://6tail.cn/calendar/api.html`. There is no English API doc. Budget time for reading
  `-sources.jar` (I did, and the Javadoc is actually thorough).
- **Source files are GBK-encoded**, not UTF-8 — mojibake if you extract the sources jar and open it
  as UTF-8 (I had to decode with code page 936). Irrelevant if you only consume the jar.
- **Java library, not Kotlin.** Getters surface as Kotlin properties (`lunar.dayInChinese`,
  `h.isWork`). Types are **platform types** (`Holiday!`, `JieQi!`) with no nullability annotations,
  so `getHoliday(...)` can return null without the compiler warning you — always use `?.`/`?:`.
  Verified: the snippets above compile cleanly under Kotlin 2.3.20.
- **Zero transitive dependencies** → no conflict with Compose Desktop 1.7.3, kotlinx-datetime
  0.6.1, or sqlite-jdbc. Bytecode targets Java 1.5+ (per README), fine on the project's JDK 21
  toolchain.
- **`HolidayUtil` is static mutable state** — `fix()` should be called once at startup.
- **Prefer `Solar.fromYmd(y,m,d)` over `Solar.fromDate(Date)`**: the latter depends on the JVM
  default time zone. I did **not** test timezone/`LunarTime` behaviour.
- Holiday data is a compile-time static string: **no network access, no runtime data fetch**.
- Requirement 3 says "e.g. 2020-2026" — **met**; 2027 data will require a library update (or your
  own `fix()` call once 国务院 publishes it, typically ~Nov 2026).

### Could NOT verify

- Whether/when 2027 holiday data will ship in a future release (no commitment found; moot until
  国务院 publishes the 2027 schedule).
- No English documentation exists to point at.
- I did not benchmark performance, nor test `Solar.fromDate(Date)` / `LunarTime` timezone semantics.
- Maven Central's *search* index reported `1.7.4` as latest while `maven-metadata.xml` and the
  repository directory reported `1.7.7`; I trusted the latter (and downloaded 1.7.7 successfully).
